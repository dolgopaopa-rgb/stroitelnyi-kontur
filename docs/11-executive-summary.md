# Executive Summary

## Что нужно разработать

Нужно разработать внутреннее веб-приложение для строительной компании.

Система должна закрыть этап после продажи: от передачи объекта из Bitrix в строительство до закрытия объекта и архива.

Bitrix остается CRM для продаж. Сметтер остается учетной системой для смет, материалов, выполнения, КС-2, КС-3 и актов.

Новая система нужна как операционный строительный контур:

- объекты;
- задачи;
- материалы;
- допработы;
- сверхбюджет;
- договоры;
- сроки;
- документы;
- фото;
- журнал решений;
- локации;
- контроль связи со Сметтером.

## Главная проблема

Сейчас рабочая информация размазана по Telegram-чатам:

- по каждому объекту есть чат с заказчиком;
- есть рабочий чат без заказчика;
- в чатах смешаны заявки, фото, решения, материалы, документы, узлы, согласования;
- нет единого архива;
- нет общей базы документов, фото и решений;
- сложно отследить допработы и увеличение затрат;
- сложно контролировать сроки договоров.

## Главная цель

Сделать систему, где вся важная информация привязана к объекту и конкретной сущности:

- задаче;
- заявке на материалы;
- допработе;
- договору;
- документу;
- фотоотчету;
- согласованию;
- событию в журнале.

## Ключевое бизнес-правило

Любая работа или закупка сверх утвержденной сметы не должна автоматически смешиваться с основной сметой.

Сверхбюджет должен иметь:

- основание;
- причину;
- сумму;
- статус;
- ответственное лицо;
- решение: заказчик, компания, подрядчик, спорно;
- связь с допником или отдельным актом.

## Пользователи

- руководитель компании;
- Артем, руководитель строительства;
- Алексей, руководитель продаж;
- Анастасия, снабженец;
- Ксения и Илья, сметчики;
- Андрей и Сергей, прорабы.

Заказчик в MVP не входит. Личный кабинет заказчика можно делать позже.

## MVP

В первую версию должны войти:

1. Пользователи и роли.
2. Объекты.
3. Карточка объекта.
4. Задачи.
5. Документы и архив.
6. Заявки на материалы.
7. Допработы и отклонения от сметы.
8. Согласования.
9. Договоры и сроки.
10. Напоминания.
11. Общий контроль сроков.
12. Фотоотчеты.
13. Журнал событий.
14. Локации объектов и поставщиков.
15. Очередь Сметтера.

При создании объекта Алексей загружает первичный список материалов из Excel-выгрузки сметы. Это нужно, чтобы прораб выбирал материалы из готового списка, а не вводил их вручную.

## Рекомендованный стек

Рекомендуемый вариант для MVP:

- Frontend: Next.js + React + TypeScript.
- Backend/BaaS: Supabase.
- База данных: PostgreSQL.
- Файлы: Supabase Storage или S3-совместимое хранилище.
- Интеграции: отдельный Node.js backend на следующем этапе.

Почему так:

- быстро запустить MVP;
- удобно делать веб-приложение с адаптацией под телефон;
- PostgreSQL хорошо подходит для связей объект-договор-смета-заявка-документ;
- можно позже добавить интеграции с Bitrix и Сметтером.

## Интеграции

### Bitrix

На первом этапе:

- ручное создание объекта;
- ссылка или ID сделки Bitrix.

Позже:

- создание объекта из сделки;
- импорт заказчика, контактов, договора и суммы.

### Сметтер

На первом этапе:

- ссылка или ID объекта/сметы;
- ручные статусы "ждет внесения", "внесено", "включено в акт";
- очередь Сметтера для Анастасии и сметчиков.

Позже:

- проверить API Сметтера;
- передавать материалы;
- получать статусы списания;
- передавать выполнение;
- получать статусы актов.

## Пилот

Пилот запускать на 2-3 объектах.

Участники пилота:

- руководитель;
- Артем;
- Анастасия;
- один сметчик;
- Андрей;
- Сергей.

На пилоте вести в системе:

- задачи;
- заявки на материалы;
- документы;
- допработы;
- договоры и сроки;
- фото;
- журнал решений;
- очередь Сметтера.

Telegram на пилоте не запрещать, но ввести правило:

- решения;
- заявки;
- документы;
- фото;
- допработы;
- сверхбюджет

должны попадать в систему.

## Критерии успешного MVP

MVP можно считать успешным, если:

- по объекту можно быстро найти договоры, сметы, акты и фото;
- заявки на материалы не теряются;
- сверхбюджет виден отдельно от основной сметы;
- допработы имеют статус и ответственное лицо;
- сроки договоров контролируются;
- важные решения фиксируются в журнале;
- Анастасии не приходится искать заявки по чатам;
- руководитель видит спорные затраты и просрочки;
- команда меньше возвращается в Telegram.

# Архитектура MVP и технический стек

## 1. Общий подход

Для первой версии лучше делать веб-приложение с адаптацией под телефон, а не отдельное мобильное приложение.

Причины:

- быстрее запустить;
- проще дорабатывать;
- пользователи смогут работать с компьютера и телефона;
- не нужно проходить публикацию в App Store / Google Play;
- легче пилотировать на 2-3 объектах.

Цель MVP: получить рабочую внутреннюю систему, обкатать процессы, а уже потом решать вопрос с полноценным мобильным приложением.

## 2. Варианты технического стека

### Вариант A. Быстрый MVP

Frontend:

- Next.js или React;
- адаптивный интерфейс;
- UI-компоненты на базе готовой библиотеки.

Backend:

- Supabase или Firebase;
- PostgreSQL в Supabase;
- встроенная авторизация;
- хранилище файлов;
- простые серверные функции.

Плюсы:

- быстро;
- дешевле на старте;
- меньше инфраструктуры;
- удобно для прототипа и пилота.

Минусы:

- часть логики зависит от платформы;
- сложные интеграции могут потребовать отдельного backend;
- в будущем может понадобиться перенос части логики.

Подходит, если нужно быстро запустить пилот и проверить процессы.

### Вариант B. Надежный production

Frontend:

- Next.js / React;
- отдельная дизайн-система;
- PWA для телефона.

Backend:

- NestJS или Django;
- PostgreSQL;
- Redis для очередей и уведомлений;
- S3-совместимое хранилище файлов;
- отдельный сервис интеграций.

Инфраструктура:

- VPS или облако;
- Docker;
- резервные копии;
- мониторинг;
- журналирование.

Плюсы:

- гибкость;
- проще делать сложные права;
- проще интегрироваться с Bitrix и Сметтером;
- лучше контроль данных.

Минусы:

- дороже;
- дольше разработка;
- нужна поддержка backend и инфраструктуры.

Подходит, если сразу планируется серьезное промышленное внедрение.

### Вариант C. Компромиссный

Frontend:

- Next.js / React.

Backend:

- Supabase как база, авторизация и файлы;
- отдельный небольшой backend для интеграций и сложной бизнес-логики.

Плюсы:

- быстрый старт;
- не запирает проект в no-code/low-code;
- можно постепенно выносить сложную логику;
- хорош для MVP с дальнейшим ростом.

Минусы:

- архитектура чуть сложнее, чем чистый Supabase;
- нужно аккуратно разделить ответственность.

Рекомендация: для вашего случая лучше начать с варианта C.

## 3. Рекомендованный стек

### Frontend

- Next.js;
- TypeScript;
- React;
- Tailwind CSS или CSS Modules;
- PWA-режим для удобства на телефоне;
- адаптивный интерфейс под мобильный экран.

Почему:

- быстро делать интерфейсы;
- хорошо подходит для внутренних систем;
- можно открыть с телефона без отдельного приложения;
- легко развивать.

### Backend

Для MVP:

- Supabase;
- PostgreSQL;
- Supabase Auth;
- Supabase Storage;
- Row Level Security для базового разграничения прав.

Для интеграций:

- отдельный Node.js backend;
- cron-задачи;
- webhooks;
- API-клиенты Bitrix и Сметтера.

### База данных

- PostgreSQL.

Почему:

- надежная реляционная модель;
- удобно хранить связи объект-договор-смета-заявка-документ;
- легко строить отчеты;
- хорошо масштабируется для внутренней системы.

### Файлы

Варианты:

- Supabase Storage;
- S3-совместимое хранилище;
- Яндекс Object Storage;
- Selectel S3;
- другое облачное S3-хранилище.

Файлы не нужно хранить прямо в базе.

В базе хранятся:

- ссылка на файл;
- тип документа;
- объект;
- автор;
- версия;
- статус;
- дата;
- права доступа.

## 5. Права доступа

Права лучше делать через роли и участие в объекте.

Уровни доступа:

- полный доступ;
- доступ ко всем строительным объектам;
- доступ только к своим объектам;
- доступ только к снабжению;
- доступ к сметам и документам;
- только просмотр.

Принцип:

- руководитель видит все;
- Артем видит строительный контур;
- Алексей может создать объект после Bitrix;
- Анастасия видит заявки, поставщиков и связанные объекты;
- сметчики видят сметы, документы, допработы и акты;
- прорабы видят только свои объекты.

## 6. Уведомления

MVP:

- уведомления внутри системы;
- список напоминаний на рабочем столе;
- контроль сроков.

Типы уведомлений:

- назначена задача;
- задача просрочена;
- создана заявка на материалы;
- заявка требует согласования;
- договор скоро заканчивается;
- документ требует согласования;
- допработа требует решения;
- сверхбюджет без решения;
- позиция ждет внесения в Сметтер.

Следующий этап:

- Telegram-уведомления;
- email;
- push-уведомления в PWA.

## 7. Интеграции

### Bitrix

Этап 1:

- ручное создание объекта;
- ссылка/ID сделки Bitrix.

Этап 2:

- кнопка "создать объект из сделки";
- импорт заказчика;
- импорт контактов;
- импорт договора;
- импорт суммы;
- импорт ответственного менеджера.

### Сметтер

Перед разработкой интеграции нужно уточнить:

- есть ли доступ к API на вашем тарифе;
- какие сущности можно читать;
- какие сущности можно создавать;
- есть ли webhooks;
- можно ли передавать материалы, работы и акты;
- можно ли получать статусы документов;
- есть ли стабильные внешние ID.

MVP без глубокой интеграции:

- хранить ссылки и ID Сметтера;
- вести очередь "ждет внесения";
- фиксировать статусы вручную;
- делать выгрузку для ручного импорта.

После проверки API:

- передавать заявки на материалы;
- передавать фактические закупки;
- получать статусы списания;
- передавать выполнение работ;
- получать статусы актов.

## 8. Схема работы данных

Основная цепочка:

`Объект -> Договор -> Смета -> Раздел работ -> Задача / Допработа -> Заявка -> Закупка -> Сметтер -> Акт`

Цепочка допработ:

`Отклонение -> Смета допработы -> Согласование -> Допник / отдельный акт -> Материалы -> Выполнение -> Сметтер -> Закрытие`

Цепочка документов:

`Документ -> Объект -> Договор / Допработа / Акт -> Срок -> Ответственный -> Журнал`

## 9. Безопасность и резервные копии

Нужно предусмотреть:

- вход по логину/паролю;
- роли и права;
- журнал действий;
- ограничение доступа к файлам;
- резервные копии базы;
- резервные копии файлов;
- защиту от случайного удаления;
- восстановление удаленных файлов/записей, если возможно.

Удаление лучше заменить архивированием:

- объект архивируется;
- документ помечается как устаревший;
- задача отменяется;
- заявка отменяется.

## 10. Пилотный запуск

Пилот лучше делать на 2-3 объектах.

Участники пилота:

- руководитель;
- Артем;
- Анастасия;
- один сметчик;
- Андрей;
- Сергей.

Что вести в системе на пилоте:

- задачи;
- заявки на материалы;
- фотоотчеты;
- допработы;
- договоры;
- документы;
- журнал решений;
- сроки;
- очередь Сметтера.

Telegram на пилоте:

- оставить как быстрый канал связи;
- все решения, файлы, заявки и фото переносить в систему;
- по итогам недели смотреть, где команда все равно уходит в чаты.

## 11. Этапы разработки

### Этап 1. Основа

- авторизация;
- роли;
- пользователи;
- объекты;
- карточка объекта;
- документы;
- задачи.

### Этап 2. Строительные процессы

- заявки на материалы;
- допработы;
- отклонения;
- согласования;
- фотоотчеты;
- журнал событий.

### Этап 3. Контроль

- договоры;
- напоминания;
- общий контроль сроков;
- локации;
- поставщики;
- очередь Сметтера.

### Этап 4. Пилот

- тестирование на реальных объектах;
- исправление сценариев;
- доработка прав;
- доработка форм;
- подготовка интеграций.

### Этап 5. Интеграции

- Bitrix;
- Сметтер;
- уведомления;
- экспорт/импорт.

## 12. Рекомендация

Рекомендуемый путь:

1. Делать веб-приложение.
2. Использовать Next.js + TypeScript на frontend.
3. Использовать PostgreSQL.
4. Для быстрого MVP взять Supabase.
5. Для интеграций добавить отдельный Node.js backend.
6. Сначала запустить пилот без глубокой интеграции со Сметтером.
7. После пилота интегрировать только те сценарии, где реально есть двойная работа.

# План разработки MVP по спринтам

## 1. Общая логика разработки

MVP лучше делать итерациями по 1-2 недели.

Цель не в том, чтобы сразу построить всю систему, а в том, чтобы быстро получить работающий строительный контур и начать проверять его на реальных объектах.

Рекомендуемый порядок:

1. Основа: пользователи, роли, объекты, карточка объекта.
2. Рабочие процессы: задачи, документы, материалы.
3. Контроль: допработы, сверхбюджет, согласования, сроки.
4. Полевая работа: фото, локации, журнал.
5. Сметтер и пилот.

## 2. Спринт 0. Подготовка

Срок: 3-5 рабочих дней.

Цель: подготовить проект к разработке.

Задачи:

- утвердить ТЗ;
- утвердить архитектуру;
- выбрать стек;
- создать репозиторий;
- настроить базовый проект;
- настроить Supabase/PostgreSQL;
- настроить хранилище файлов;
- подготовить окружения: dev и staging;
- завести тестовых пользователей.

Результат:

- проект запускается;
- есть пустое приложение;
- есть база;
- есть авторизация;
- есть тестовые роли.

## 3. Спринт 1. Пользователи, роли, объекты

Срок: 1-2 недели.

Цель: сделать основу системы.

Функции:

- вход в систему;
- роли пользователей;
- список объектов;
- создание объекта после Bitrix;
- первичная загрузка Excel-выгрузки материалов по смете;
- карточка объекта;
- участники объекта;
- базовые статусы объекта;
- ссылки на Bitrix и Сметтер;
- адрес и ссылка на навигатор.

Экраны:

- вход;
- рабочий стол;
- список объектов;
- карточка объекта;
- форма создания объекта.

Критерии готовности:

- руководитель видит все объекты;
- Артем видит строительные объекты;
- прораб видит только свои объекты;
- можно создать объект;
- Алексей может приложить первичный список материалов при создании объекта;
- можно назначить прораба, сметчика и снабженца;
- объект открывается и показывает основные данные.

## 4. Спринт 2. Задачи и документы

Срок: 1-2 недели.

Цель: заменить часть рабочих поручений и файлов из Telegram.

Функции:

- создание задач;
- назначение исполнителей;
- сроки задач;
- статусы задач;
- вкладка задач в объекте;
- архив документов;
- добавление документа;
- типы документов;
- версии документов;
- ответственный за документ;
- срок действия или согласования документа.

Экраны:

- задачи;
- форма задачи;
- документы;
- форма документа;
- вкладки объекта: задачи, документы.

Критерии готовности:

- задачу можно создать из общего раздела;
- задача привязана к объекту;
- задача видна в карточке объекта;
- документ можно добавить в архив;
- документ имеет тип, версию и ответственного;
- документ виден внутри объекта.

## 5. Спринт 3. Материалы и снабжение

Срок: 1-2 недели.

Цель: вынести заявки на материалы из чатов.

Функции:

- создание заявки на материалы;
- основание заявки;
- список материалов;
- срок поставки;
- статус закупки;
- поставщик;
- счет/накладная;
- статус учета в Сметтере;
- предупреждение при заявке сверх основной сметы;
- вкладка материалов в объекте.

Экраны:

- материалы;
- форма заявки;
- карточка заявки;
- вкладка материалов в объекте.

Критерии готовности:

- прораб может создать заявку;
- Анастасия видит новую заявку;
- заявка имеет основание;
- заявка сверх основной сметы помечается отдельно;
- заявка может получить статус доставки;
- заявка может получить статус Сметтера.

## 6. Спринт 4. Допработы, отклонения и согласования

Срок: 1-2 недели.

Цель: перестать смешивать сверхбюджет с основной сметой.

Функции:

- создание допработы;
- создание отклонения от сметы;
- тип отклонения;
- сумма;
- причина;
- статус;
- решение по деньгам;
- связь с заявками на материалы;
- связь с документами;
- согласования;
- отдельный список позиций, требующих решения.

Экраны:

- допработы;
- форма допработы;
- согласования;
- вкладка допработ в объекте;
- контроль объекта.

Критерии готовности:

- можно создать допработу;
- можно зафиксировать перерасход;
- можно указать решение: заказчик, компания, подрядчик, спорно;
- позиция без решения видна руководителю;
- заявка на материалы может быть связана с допработой;
- сверхбюджет не попадает в обычный поток без классификации.

## 7. Спринт 5. Договоры, сроки и напоминания

Срок: 1-2 недели.

Цель: не пропускать окончания договоров и важные сроки.

Функции:

- создание договора;
- тип договора;
- дата начала и окончания;
- ответственный;
- статус договора;
- допсоглашения;
- напоминания за 30/14/7 дней;
- общий экран сроков;
- просроченные сроки;
- сроки по задачам, заявкам, документам и согласованиям.

Экраны:

- договоры;
- форма договора;
- контроль сроков;
- напоминания на рабочем столе.

Критерии готовности:

- договор имеет дату окончания;
- договор попадает в контроль сроков;
- система показывает договоры, которые скоро заканчиваются;
- просроченные сроки подсвечиваются;
- ответственный видит свои напоминания.

## 8. Спринт 6. Фото, журнал и локации

Срок: 1-2 недели.

Цель: закрыть полевую работу и историю решений.

Функции:

- фотоотчеты;
- отметка "можно заказчику";
- связь фото с задачей, допработой или заявкой;
- журнал событий;
- фиксация решений;
- фиксация проблем;
- локации объектов;
- локации поставщиков.

Экраны:

- фото;
- форма фотоотчета;
- журнал;
- форма события;
- локации.

Критерии готовности:

- прораб может добавить фотоотчет;
- фото видно в объекте;
- важное решение можно записать в журнал;
- журнал виден внутри объекта;
- локации объектов и поставщиков доступны из одного раздела.

## 9. Спринт 7. Очередь Сметтера и подготовка пилота

Срок: 1-2 недели.

Цель: подготовить систему к реальной работе и уменьшить двойной ввод.

Функции:

- очередь Сметтера;
- статусы внесения;
- ручная отметка "внесено";
- ручная отметка "включено в акт";
- выгрузка списка позиций;
- проверка API/экспорта Сметтера;
- подготовка тестовых объектов.

Экраны:

- очередь Сметтера;
- фильтры по статусу;
- карточка позиции очереди;
- выгрузка.

Критерии готовности:

- Анастасия видит, что нужно внести в Сметтер;
- сметчик видит, что нужно проверить;
- позиции без решения по основанию подсвечиваются;
- можно отследить, что попало в акт.

## 10. Спринт 8. Пилот

Срок: 2-4 недели.

Цель: проверить систему на реальных объектах.

Как запускать:

- выбрать 2-3 объекта;
- назначить участников;
- перенести базовые документы;
- вести задачи в системе;
- вести заявки на материалы в системе;
- вести фотоотчеты в системе;
- фиксировать допработы и сверхбюджет в системе;
- фиксировать решения в журнале;
- каждую неделю собирать обратную связь.

Участники:

- руководитель;
- Артем;
- Анастасия;
- Ксения или Илья;
- Андрей;
- Сергей.

Критерии успешного пилота:

- по пилотным объектам можно найти все ключевые документы;
- заявки на материалы не теряются;
- сверхбюджет виден отдельно;
- договоры и сроки контролируются;
- фотоотчеты не ищутся в чатах;
- решения фиксируются в журнале;
- команда меньше возвращается в Telegram.

## 11. Что можно отложить после MVP

- личный кабинет заказчика;
- автоматический импорт Telegram;
- сложная аналитика;
- мобильное приложение;
- полная интеграция со Сметтером;
- глубокая интеграция с Bitrix;
- BI-дашборды;
- электронная подпись.

## 12. Риски разработки

### Риск 1. Попытка заменить Сметтер

Не нужно делать свой Сметтер.

Решение:

- оставить Сметтер учетной системой;
- новая система отвечает за процессы, основания, контроль и связи.

### Риск 2. Слишком много функций в первой версии

Если пытаться сделать все сразу, запуск затянется.

Решение:

- сначала объекты, задачи, материалы, документы;
- затем допработы, сроки, фото, журнал;
- интеграции после пилота.

### Риск 3. Команда продолжит писать в Telegram

Решение:

- не запрещать Telegram резко;
- сделать правило: решения, заявки, документы и фото должны попадать в систему;
- каждую неделю смотреть, что не прижилось.

### Риск 4. Нет интеграции со Сметтером

Решение:

- начать с ручной очереди;
- проверить API;
- интегрировать только самые болезненные сценарии.

### Риск 5. Неправильные права доступа

Решение:

- начать с простых ролей;
- добавить project_members;
- расширять права после пилота.

## 13. Минимальная версия для первого показа

Самый маленький демонстрируемый результат:

- вход;
- список объектов;
- карточка объекта;
- задачи;
- документы;
- заявки на материалы;
- допработы;
- договоры и сроки.

Это уже можно показать команде и собрать обратную связь.

## 14. Минимальная версия для пилота

Для пилота обязательно нужны:

- роли;
- объекты;
- задачи;
- материалы;
- документы;
- допработы;
- договоры;
- контроль сроков;
- фото;
- журнал;
- локации;
- очередь Сметтера.

## 15. Рекомендованный порядок запуска

1. Собрать MVP на тестовых данных.
2. Показать руководителю и Артему.
3. Поправить структуру карточки объекта.
4. Показать Анастасии и прорабам.
5. Поправить заявки и фото.
6. Подключить 2-3 реальных объекта.
7. Провести пилот 2-4 недели.
8. По итогам пилота решить, какие интеграции делать первыми.

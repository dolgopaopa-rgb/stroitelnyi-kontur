# Санитизированная переписка и контекст проекта

Дата фиксации: 2026-05-21 08:28

Этот файл нужен, чтобы продолжить работу с другого компьютера без потери контекста. Это не хранилище паролей. Все логины, пароли, токены, OAuth-коды, SSH-ключи и прочие секреты намеренно не записаны в этот файл и не должны попадать в GitHub.

## 1. Идея проекта

Руководитель строительной компании хочет внутреннее приложение, чтобы не плодить рабочие чаты в мессенджерах и собрать процесс строительства в одном месте.

Основная логика:

- Bitrix остается CRM для продаж.
- Новый контур нужен в первую очередь для этапа строительства после подписания договора и оплаты.
- Алексей, менеджер, заводит карточку клиента/объекта и передает объект в строительство.
- Руководитель строительства принимает объект в работу, проверяет документы, назначает ответственных.
- Прорабы, снабжение, сметчики и технадзор работают уже внутри объекта.
- Документы, фотографии, узлы, заявки, работы, материалы, допработы и история должны храниться в единой базе.

## 2. Роли и люди

Рабочие роли:

- Ген.директор: руководит всем процессом.
- Фин.директор: добавлен позже, полный обзор без удаления.
- Бухгалтер: добавлен как заготовка под будущий финансовый учет.
- Артем: руководитель строительства.
- Алексей: менеджер / руководитель продаж, заводит объект и первичные документы.
- Анастасия: снабжение.
- Ксения и Илья: сметчики.
- Андрей и Сергей: прорабы.
- Технадзор: отдельная роль, добавлена в процессе обсуждения.

## 3. Объекты

По объектам нужна многоступенчатая передача:

1. Менеджер создает карточку объекта.
2. Менеджер заполняет обязательные поля и прикладывает документы.
3. Менеджер нажимает "Передать в работу".
4. Руководитель строительства получает уведомление, проверяет объект.
5. Если все нормально, руководитель строительства принимает объект в работу.
6. Если что-то не так, возвращает менеджеру на доработку с комментарием.
7. После принятия уведомления и доступ получают прораб, снабжение, сметчики и технадзор.

Важные решения:

- Версию сметы из карточки объекта убрали.
- Поля Bitrix и Smetter стали ссылками.
- Bitrix временно убирается из интерфейса там, где он не нужен.
- Адрес объекта должен открывать Яндекс Карты.
- Завершенные объекты не удаляются, а уходят в архив.
- Из архива объект можно вернуть в работу.
- Окончательно удалять объект может только ген.директор.
- При архивации объекта связанные задачи и заявки не должны оставаться в активных реестрах.

## 4. Документы и база знаний

Изначальный раздел "Документы" переименован в "База знаний".

База знаний предназначена для:

- регламентов;
- проектных решений;
- узлов;
- инструкций;
- общей документации;
- материалов, которые нужны всем или отдельным ролям.

Документы конкретного объекта хранятся внутри карточки объекта. В базе знаний не нужно дублировать объектовые документы.

Подключен Яндекс.Диск как внешнее хранилище файлов. Секреты подключения не фиксируются в репозитории.

## 5. Сметтер и материалы

Из Сметтера выгружается файл материалов по смете. На первом этапе файл вручную загружает Алексей при создании карточки объекта.

Логика материалов:

- Прораб не вводит материалы вручную, а выбирает их из заранее загруженного списка.
- Список должен повторять разделы из выгрузки Сметтера.
- Разделы при создании заявки должны быть свернуты.
- Прораб раскрывает нужный раздел и выбирает материалы.
- Если количество по смете совпадает, строка зеленая.
- Если меньше, строка желтая.
- Если больше, строка красная.
- Превышение должно попадать как сверхсметный материал с указанием причины.
- Дополнительные материалы добавляются отдельными полями: материал, наименование, количество, причина.
- Причины: доп, замена, превышение.

Процесс заявки:

1. Прораб создает заявку.
2. Выбирает материалы из сметы и/или добавляет дополнительные.
3. Указывает желаемую дату доставки.
4. Если доставка сегодня или завтра, заявка считается срочной.
5. Снабжение получает уведомление.
6. Снабжение принимает заявку в работу или возвращает на доработку.
7. После обработки снабжение указывает фактическую/плановую дату доставки и комментарии.
8. Прораб подтверждает получение материалов.
9. Если есть проблема, прораб добавляет комментарий, фото или видео.
10. Снабжение должно исправить проблему и уведомить участников о повторной доставке или замене.

Дополнительные правила:

- Если снабжение еще не взяло заявку в работу, прораб может изменить или удалить заявку.
- Если снабжение взяло заявку в работу, прораб не может ее менять или удалять.
- Выполненные заявки через 2 дня должны уходить в архив пообъектно.
- Снабжение и руководители должны иметь выгрузку выполненных заявок.

## 6. Работы

Был добавлен раздел "Работы".

Логика:

- При создании объекта менеджер загружает из Сметтера файл "Задание на работы".
- Из файла задания на работы нужно брать только работы.
- Материалы, которые Сметтер иногда вставляет ниже в этот же файл, нужно игнорировать.
- Материалы загружаются отдельным файлом с ценами.
- Работы показываются по объекту и по разделам.
- Разделы свернуты, прораб раскрывает нужный раздел.
- Работы можно выгрузить для рабочих в PDF.
- Можно добавить появившиеся работы: наименование, единица измерения, количество, причина.
- Причины появившихся работ: доп, превышение, расходы компании, переделки.

Позже внешний вид работ был уплотнен: меньше шрифт, компактнее разделы, суммы должны помещаться.

## 7. Допработы

Раздел "Допработы" должен включать не только допматериалы, но и допработы.

Источники допработ:

- сверхсметные материалы из заявок;
- дополнительные или превышенные работы;
- ошибки сметы;
- переделки;
- расходы компании.

Важные решения:

- Снабжение не решает, создавать допработу или нет. Снабжение только получает уведомление о дополнительных материалах.
- Решение по допработе принимает прораб и руководство.
- По допработам нужно видеть список позиций и иметь возможность выгрузить их в Excel.
- Прорабам можно показывать допработы по своим объектам без финансовых сумм.

## 8. Задачи

Задачи должны быть сгруппированы по объектам, чтобы не было общего хаотичного списка.

Логика задачи:

1. Постановщик создает задачу.
2. Указывает исполнителя.
3. Указывает, кому исполнитель сдает выполнение.
4. Исполнитель видит уведомление.
5. Исполнитель ставит статус "Выполнено".
6. Проверяющий получает уведомление.
7. Проверяющий принимает выполнение или возвращает на доработку.
8. Если задача возвращена, исполнитель снова должен иметь кнопку "Выполнено".

Нужны:

- статусы задачи;
- история прохождения;
- комментарии возврата;
- срок выполнения при повторной постановке;
- возможность удаления задач только для ген.директора и руководителя строительства.

Календарный график задач пробовали, но он получился неудачным и был убран.

## 11. MAX-бот и обратная связь

Существующий бот MAX был временно переориентирован под контур обратной связи.

Логика:

- бот добавлен в чат обсуждения программы;
- сообщения из чата попадают в раздел "Обратная связь";
- фото и видео должны прикрепляться к сообщениям;
- подписи к фото и видео должны быть видны;
- на сообщениях есть действия;
- можно выбирать несколько сообщений и удалять скопом;
- при внесении изменений бот должен отправлять в чат краткий отчет о выполненных работах.

Важное ограничение:

- Бот сам не начинает программировать по сообщениям из чата.
- Он собирает обратную связь и помогает сформировать ТЗ.
- Работа начинается после явной команды в Codex.
